---
title: "Workflows"
description: "Führe Dateioperationen beim Starten und Stoppen eines Servers oder bei Bedarf aus"
---

Workflows führen eine Abfolge von Dateioperationen auf einem Serverhost aus. Du kannst sie manuell oder bei jedem Start und Stopp eines Servers ausführen.

In dieser Anleitung erstellst du einen Backup-Workflow, führst ihn im Dashboard aus und erfährst anschließend, wie du ihn anpasst.

## Backup-Workflow ausführen

<Steps>
  <Step title="Workflow erstellen">
    Erstelle die Datei `workflows/default/backup.yml` in deinem Serverhost-Verzeichnis:

    ```yaml workflows/default/backup.yml
    name: Backup Workflow

    steps:
      - name: copy-running-to-backup
        uses: simplecloud/copy
        with:
          from: "{{ runtime.server-dir }}"
          to: "{{ runtime.templates }}/.backup/{{ runtime.name }}/{{ time.now.date }}/{{ time.now.dateTime }}-{{ runtime.nice-id }}-{{ runtime.process-id }}"
          init-dir-if-missing: true
    ```
  </Step>

  <Step title="Workflow laden">
    Starte den Serverhost neu. SimpleCloud verwendet den Dateipfad als Workflow-ID. Dieser Workflow erhält daher die ID `default/backup`.
  </Step>

  <Step title="Workflow zuweisen">
    Öffne im Dashboard eine Servergruppe oder einen persistenten Server und gehe zu **Settings > Workflows**. Füge unter **Manual Workflows** den Eintrag `default/backup` hinzu.
  </Step>

  <Step title="Workflow ausführen">
    Starte den Server, falls er noch nicht läuft. Öffne anschließend sein Aktionsmenü und führe zum Testen `default/backup` aus.
  </Step>

  <Step title="Backup prüfen">
    Öffne auf dem Serverhost dieses Verzeichnis:

    ```text
    templates/.backup/<name>/<date>/<date-time>-<server>-<process-id>/
    ```

    Prüfe, ob das Zielverzeichnis die erwarteten Dateien enthält. Zeitstempel und Prozess-ID trennen die einzelnen Backup-Läufe voneinander.
  </Step>
</Steps>

<Note>
  Ein Workflow ist nur auf Serverhosts verfügbar, auf denen seine Datei vorhanden ist. Wenn die betroffenen Server auf mehreren Serverhosts ausgeführt werden können, füge jedem von ihnen dieselbe Datei hinzu und starte die Serverhosts neu.
</Note>

Bei der manuellen Aktion werden die Dateien kopiert, während der Minecraft-Server läuft. Dateien, die sich während des Kopierens ändern, etwa Welten und Plugin-Daten, ergeben möglicherweise kein konsistentes Backup. Füge für solche Dateien `default/backup` unter **On Stop Workflows** hinzu und stoppe den Server normal. Stop-Workflows werden ausgeführt, nachdem der Serverprozess beendet wurde.

Platziere `default/backup` vor `internal/cleanup`.

<Warning>
  `internal/cleanup` entfernt das laufende Verzeichnis eines Gruppenservers. Jeder Workflow, der dieses Verzeichnis liest, muss vor dem Cleanup ausgeführt werden.
</Warning>

<Note>
  Dieser Workflow erstellt Dateikopien, testet jedoch keine Wiederherstellungen und entfernt keine alten Backups. Prüfe, ob du die benötigten Daten wiederherstellen kannst, und lege eine Aufbewahrungsstrategie für `templates/.backup/` fest.
</Note>

## Workflow-Datei verstehen

Der Backup-Workflow hat dieselbe grundlegende Struktur wie jeder andere Workflow:

- `name` identifiziert den Workflow in den Serverhost-Logs.
- `steps` enthält die Operationen in ihrer Ausführungsreihenfolge.
- `name` innerhalb eines Steps identifiziert diesen Step in den Logs.
- `uses` wählt die Aktion aus. Dieser Workflow verwendet `simplecloud/copy`.
- `with` enthält die von der Aktion benötigten Werte.

In diesem Workflow verweist `from` auf das laufende Serververzeichnis. `to` erzeugt einen eindeutigen Backup-Pfad. Fehlt die Quelle, erstellt `init-dir-if-missing: true` ein leeres Quellverzeichnis, anstatt einen Fehler auszulösen. Prüfe immer, ob das fertige Backup die erwarteten Dateien enthält.

### Vom Workflow verwendete Werte

Werte innerhalb von `{{ ... }}` werden beim Ausführen des Workflows ersetzt.

| Wert | Ergebnis |
| --- | --- |
| `{{ runtime.server-dir }}` | Laufendes Serververzeichnis |
| `{{ runtime.templates }}` | Template-Verzeichnis des Serverhosts |
| `{{ runtime.name }}` | Name der Servergruppe oder des persistenten Servers |
| `{{ runtime.nice-id }}` | Name des laufenden Servers, zum Beispiel `lobby-1` |
| `{{ runtime.process-id }}` | ID des laufenden Prozesses |
| `{{ time.now.date }}` | Aktuelles Datum |
| `{{ time.now.dateTime }}` | Aktuelles Datum und aktuelle Uhrzeit |

## Backup-Workflow anpassen

Verwende den Backup-Workflow als Ausgangspunkt:

<Steps>
  <Step title="Workflow kopieren">
    Kopiere `workflows/default/backup.yml` an einen neuen Pfad, zum Beispiel `workflows/custom/world-backup.yml`.
  </Step>

  <Step title="Workflow ändern">
    Gib ihm einen neuen `name` und passe anschließend die Kopierpfade und Ausschlüsse an deine Aufgabe an.
  </Step>

  <Step title="Workflows neu laden">
    Starte jeden Serverhost neu, auf dem die neue Datei vorhanden ist.
  </Step>

  <Step title="Neue ID zuweisen">
    Füge unter **Settings > Workflows** den Eintrag `custom/world-backup` hinzu. Die Workflow-ID entspricht immer dem Pfad unterhalb von `workflows/`, jedoch ohne `.yml`.
  </Step>
</Steps>

### Kopierumfang ändern

Die Aktion `simplecloud/copy` unterstützt unter `with` diese Einstellungen:

| Einstellung | Zweck |
| --- | --- |
| `from` | Zu kopierende Datei oder zu kopierendes Verzeichnis |
| `to` | Ziel des Kopiervorgangs |
| `replace` | Gibt an, ob vorhandene Dateien überschrieben werden; Standardwert ist `true` |
| `exclude` | Pfad oder Liste von Pfaden, die ausgelassen werden |
| `init-dir-if-missing` | Gibt an, ob das Quellverzeichnis erstellt wird, wenn es nicht existiert; Standardwert ist `false` |

Füge beispielsweise eine `exclude`-Liste hinzu, um Logs und Caches auszulassen, während der Rest des Backups unverändert bleibt:

```yaml
with:
  from: "{{ runtime.server-dir }}"
  to: "{{ runtime.templates }}/.backup/{{ runtime.name }}/{{ time.now.date }}/{{ time.now.dateTime }}-{{ runtime.nice-id }}-{{ runtime.process-id }}"
  init-dir-if-missing: true
  exclude:
    - "logs/**"
    - "cache/**"
```

Muster unter `exclude` sind relativ zu `from`.

## Verfügbare Aktionen

<AccordionGroup>
  <Accordion title="Dateien kopieren">
    `simplecloud/copy` kopiert eine Datei oder ein Verzeichnis von `from` nach `to`. Mit `replace` legst du fest, ob vorhandene Dateien überschrieben werden. Mit `exclude` lässt du passende Pfade aus.
  </Accordion>

  <Accordion title="Archive erstellen oder entpacken">
    `simplecloud/compress` erstellt ein Archiv und `simplecloud/decompress` entpackt eines. Beide Aktionen benötigen `from` und `to`; `replace` ist optional. Der Dateiname des Archivs bestimmt sein Format.
  </Accordion>

  <Accordion title="Datei hochladen">
    `simplecloud/upload` sendet die Datei unter `from` an die URL unter `to`. Die Aktion lädt Dateien hoch, keine Verzeichnisse. Du kannst außerdem die HTTP-`method` und einen Wert für `authorization-bearer` festlegen.

    <Warning>
      Workflow-Dateien enthalten Klartext. Speichere darin keine langlebigen Zugriffstokens.
    </Warning>
  </Accordion>

  <Accordion title="Dateien löschen">
    `simplecloud/delete` entfernt den unter `path` angegebenen Inhalt. Verwende `min-age`, zum Beispiel `7d`, um neuere Dateien zu behalten.

    <Warning>
      Löschpfade sind nicht auf das Serververzeichnis beschränkt. Prüfe den endgültigen Pfad, bevor du den Workflow ausführst.
    </Warning>
  </Accordion>

  <Accordion title="Steps wiederholen">
    `simplecloud/foreach` führt verschachtelte Steps für jeden Eintrag unter `items` aus. Lege mit `as` den Variablennamen fest, den die verschachtelten `steps` verwenden.
  </Accordion>
</AccordionGroup>

## Eingebaute Workflows

| Workflow | Zweck |
| --- | --- |
| `internal/setup` | Bereitet das Serververzeichnis vor dem Start vor |
| `internal/cleanup` | Bereinigt Dateien, nachdem der Server gestoppt wurde |

<Warning>
  Lass `internal/setup` und `internal/cleanup` zugewiesen, sofern du ihr Verhalten nicht bewusst ersetzt.
</Warning>

## Fehlerbehebung

<AccordionGroup>
  <Accordion title="Der Workflow wird nicht aufgelistet">
    Workflow-IDs werden manuell im Dashboard eingetragen. Prüfe, ob die Datei auf dem Serverhost vorhanden ist, starte den Serverhost neu und füge die ID erneut hinzu.
  </Accordion>

  <Accordion title="Der Workflow wird nicht gefunden">
    Prüfe, ob die ID dem Dateipfad entspricht. `custom/world-backup` muss beispielsweise auf `workflows/custom/world-backup.yml` verweisen.
  </Accordion>

  <Accordion title="Ein Backup fehlt">
    Suche in den Serverhost-Logs nach `Backup Workflow` und `copy-running-to-backup`. Prüfe bei einem automatischen Backup außerdem, ob `default/backup` vor `internal/cleanup` steht.
  </Accordion>
</AccordionGroup>
