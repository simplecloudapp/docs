## Overview

The Server Connection plugin is the central routing plugin for SimpleCloud proxies. It registers available SimpleCloud servers on the proxy, removes them again when they stop, sends players to the correct join targets, and redirects players to fallback targets when their current server becomes unavailable.

It also lets you define player-facing commands such as `/lobby`, `/hub`, or `/leave` that send players to the least populated matching target.

<Note>
  Server registration is part of Server Connection. You do not need a separate
  registration plugin for proxy registration, external servers, join targets, or
  fallback routing.
</Note>

## Quick Setup

<Steps>
  <Step title="Install the plugin">
    Download the plugin from [GitHub](https://github.com/simplecloudapp/server-connection-plugin/releases) and place it in your proxy template's `plugins/` folder.
  </Step>

  <Step title="Install the API plugin">
    Make sure the `simplecloud-api` plugin is installed on the same proxy template. Server Connection uses it to read SimpleCloud servers and events.
  </Step>

  <Step title="Generate configuration files">
    Start the proxy once so the plugin creates `config.yml`, `commands.yml`, and `messages.yml`.
  </Step>

  <Step title="Configure routing">
    Edit the generated files to define registered server names, connection groups, join targets, fallback targets, and player commands.

    <Check>
      After reloading or restarting the proxy, `/connection reload` should reload all Server Connection configuration files without errors.
    </Check>
  </Step>
</Steps>

## Generated Files

| File | Purpose |
| ---- | ------- |
| `config.yml` | Registration, address routes, connection targets, network join targets, and fallbacks |
| `commands.yml` | Player commands such as `/lobby` and `/hub` |
| `messages.yml` | Kick messages and `/connection reload` messages |

## Server Registration

Server registration is the part of Server Connection that makes servers visible to the proxy. When it is enabled, the plugin keeps the proxy's server list synchronized with SimpleCloud server events.

When registration is enabled, the plugin clears existing proxy server entries on startup, registers any `additionalServers`, loads currently available SimpleCloud game servers, and watches server events.

Only servers with group type `SERVER` are registered. Servers using the `standalone` blueprint configurator are skipped.

```yaml
version: 1

registration:
  enabled: true
  serverNamePattern: "<group>-<numerical_id>"
  persistentServerNamePattern: "<name>"
  ignoreServerGroupsAndPersistentServers: []
  additionalServers:
    - name: "external-lobby"
      address: "127.0.0.1"
      port: 25565
```

### Register an External Server

Use `additionalServers` for servers that should be visible to the proxy but are not managed by SimpleCloud.

```yaml
registration:
  enabled: true
  additionalServers:
    - name: "external-lobby"
      address: "127.0.0.1"
      port: 25565
```

External servers can be matched by `connections` like any other registered proxy server.

### Registration Placeholders

| Placeholder | Description |
| ----------- | ----------- |
| `<group>` | Group name for group-based servers |
| `<name>` | Persistent server name |
| `<numerical_id>` | Group server numerical ID |
| `<id>` | Server UUID |

Custom server properties are also available as MiniMessage placeholders. Property names are lowercased and `-` is replaced with `_`.

## Connections

A connection is a named group of registered servers. The default configuration creates a `lobby` connection that matches registered server names starting with `lobby`.

```yaml
connections:
  - name: "lobby"
    serverNameMatcher:
      operation: "STARTS_WITH"
      value: "lobby"
      negate: false
    rules: []
```

Rules can restrict a connection by permission or environment variable. If a rule has a `bypassPermission`, players with that permission skip the rule.

```yaml
connections:
  - name: "vip-lobby"
    serverNameMatcher:
      operation: "STARTS_WITH"
      value: "vip-lobby"
      negate: false
    rules:
      - type: "PERMISSION"
        name: "network.vip"
        value: "true"
        bypassPermission: "network.admin"
```

## Address Routes

Address routes send players to a connection based on the hostname they used to join the proxy. This is useful when `play.example.com` and `events.example.com` should land in different lobbies.

```yaml
address:
  routes:
    - subdomain: "events.example.com"
      targetConnection: "event-lobby"
```

If no address route matches, the plugin falls back to `networkJoinTargets`.

## Network Join Targets

Network join targets decide where a player goes when they join the proxy. Higher priorities are tried first.

```yaml
networkJoinTargets:
  enabled: true
  targetConnections:
    - name: "lobby"
      priority: 0
```

## Fallback Targets

Fallback targets decide where a player goes after a kick or server shutdown. Use `from` to limit a fallback target to players coming from specific connection names.

```yaml
fallback:
  enabled: true
  targetConnections:
    - name: "lobby"
      priority: 0
      from: []
```

## Player Commands

Player commands are configured in `commands.yml`. Each command points at one or more fallback-style target connections and sends the player to the least populated matching server.

```yaml
version: 1

commands:
  - name: "lobby"
    aliases:
      - "l"
      - "hub"
      - "quit"
      - "leave"
    permission: ""
    messages:
      alreadyConnected: "<color:#dc2626>You are already connected to this lobby!"
      noTargetConnectionFound: "<color:#dc2626>Couldn't find a target server!"
    targetConnections:
      - name: "lobby"
        priority: 0
        from: []
```

## Admin Command

| Command | Permission | Description |
| ------- | ---------- | ----------- |
| `/connection reload` | `simplecloud.connection.reload` | Reload `config.yml`, `commands.yml`, and `messages.yml` |

## How Routing Works

1. The plugin sorts the configured target connections by priority.
2. It skips targets whose `from` filter does not match the player's current connection.
3. It finds the named connection in `config.yml`.
4. It checks the connection rules.
5. It collects all registered server names that match the connection matcher.
6. It connects the player to the least populated matching server.
7. If no target works, the configured no-target message is shown or the player is kicked.

<Tip>
  Use one connection per logical destination, such as `lobby`, `minigames`, or
  `vip-lobby`, then reference those connection names from join targets,
  fallbacks, and commands.
</Tip>
